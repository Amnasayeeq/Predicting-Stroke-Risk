1. Problem Statement

Business problem:

Stroke is one of the top two causes of death in the world. A health insurer / primary-care network would like to identify patients who are at high risk of stroke before they become stroke patients to enable their prioritisation for having a preventive checkup (blood-pressure control, lifestyle counselling, review on anticoagulation etc.).

Why it is important to the company:

Early risk flagging will decrease the number of admission to hospital in an emergency, disability after sickness or disability following hospitalisation, enable a small clinical team to attend to people with the highest risk—with limited time on everyone equally, and to improve outcomes.

Data collection:

These data would be obtained from patients' electronic health records (EHRs): Demographics, vital signs (blood glucose, BMI), comorbidities (hypertension, heart disease), and lifestyle information (smoking status, work type). For this project we use a public Kaggle dataset of 'Stroke Prediction' with fedesoriano, which is also similar to the type of EHR extract (this just has only 5,110 patients and 12 columns).

ML formulation. This is a two-class classification problem:

  • Input X:Take patient demographic, clinical and lifestyle attributes.
  • Output y:stroke (1 = had a stroke, 0 = did not).

The model to be used should be intended to generate a probability (risk score) and not simply a hard classification, providing clinicians with a guidance on how to classify or prioritise patients by risk range rather than a single score.

2. Data Exploration

Data quality

  • Standard missing value counts: ~201 missing values in the bmi column (≈3.9% of the rows), no other column has missing values.

  • Duplicate / irrelevant column: id A unique identifier of a patient, ID does not include predictive information — ID is dropped before modelling.

  • Rare categories: gender has a single "Other" row; work_type has very few "Never_worked" rows. Both are kept (one-hot encoding handles them), but they contribute little statistical power.

Class imbalance

Only ~4.9% of patients in this dataset had a stroke (249 of 5,110). This is highly skewed target and has two impacts:

  • Accuracy is misleading — It is impossible to decide accuracy, as 1 would predict “no stroke” all the time, with an accuracy of ~95%, but would have no clinical relevance.

Instead we use recall (sensitivity),** F1-score, ROC-AUC and PR-AUC –** and we create the imbalance during training via the class_weight argument, which we set to 'balanced', because of the cost difference between missing out on the at-risk patient (false negative) and the unnecessary check-up (false positive).

Sampling / balancing

Because the absolute number of positive cases is small, class weights are used instead of oversampling using SMOTE but they do reduce the number of representative samples for the majority class.Since there are little number of positive cases, we don't work with undersampling because the majority class would be discarded, but don't use oversampling in SMOTE technique which would necessitate using many samples.

3. Data Preprocessing and Feature Engineering

Steps applied (for avoiding leakage, only fit during the training split):

  1. Drop id — which are NOT predictive.

  2. Train/test split — Data split is trained and tested 80/20 based on the stroke stratified data keeping the same positive rate of ~4.9% for both the trained set and the test set.

  3. New feature — age_group: bucket by age into clinically meaningful bands (child, adult, middle_age, senior) in addition to age which is a continuous variable, to facilitate non-linear age thresholds being picked up by a tree model.

  4. New feature — glucose_risk: avg_glucose_level > 140 binary type flag indicating whether the glucose value is above the diabetes threshold of 140 (pre-diabetic/diabetic) or not.

  5. Impute bmi — median impute (handling BMI outliers).

  6. Encode categoricals Categoricals (gender, ever_married, work_type, Residence_type, smoking_status, age_group)— One Hot Encoding.

  7. Scale numerics — most commonly for logistic regression model baseline, tree numerics are scale-invariant but it won't cause any harm.

All elements are encapsulated in a single scikit-learn Pipeline + ColumnTransformer, it means the same transformation will automatically happen at the time of inference.

4. Model Training & Hyperparameter Tuning

Comparing three families of models which were all configured with class_weight='balanced' when it was parameterizable:

  • Logistic Regression — linear baseline model that is easily interpretable in terms of risk multipliers (coefficients).
  • Random Forest — contains non-linear interactions (e.g. age x hypertension).
  • Gradient Boosting — typically the top-notch presenter for tabular data, but with a lack of interpretability (addressed later with SHAP).

Stratified 5-fold cross validation is used to tune parameters, and F1-score, a combination of precision and recall, is used to do so best suited to this clinically-costly-false-negative scenario than accuracy.

#seting-up,K-fold cross-validation to preserve class distribution

cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=RANDOM_STATE)

#defining model dictionary containing pipelines

models = {
    'logreg': (
        Pipeline([('prep', preprocessor), ('clf', LogisticRegression(class_weight='balanced', max_iter=1000))]),
        {'clf__C': [0.01, 0.1, 1, 10]}
    ),
    'random_forest': (
        Pipeline([('prep', preprocessor), ('clf', RandomForestClassifier(class_weight='balanced', random_state=RANDOM_STATE))]),
        {'clf__n_estimators': [200, 400], 'clf__max_depth': [4, 8, None], 'clf__min_samples_leaf': [1, 5]}
    ),
    'gradient_boosting': (
        Pipeline([('prep', preprocessor), ('clf', GradientBoostingClassifier(random_state=RANDOM_STATE))]),
        {'clf__n_estimators': [100, 200], 'clf__max_depth': [2, 3], 'clf__learning_rate': [0.05, 0.1]}
    ),
}
#initializing containers for best estimators
#storing the best results for each model
best_estimators, cv_scores = {}, {}
for name, (pipe, grid) in models.items():
    gs = GridSearchCV(pipe, grid, scoring='f1', cv=cv, n_jobs=-1)
    gs.fit(X_train, y_train)
    best_estimators[name] = gs.best_estimator_
    cv_scores[name] = gs.best_score_

    print(f"{name}: best CV F1 = {gs.best_score_:.3f}, best params = {gs.best_params_}")

We re-train the best model family with SMOTE (Synthetic Minority Over-sampling) inside the CV loop (we do not use SMOTE on the test set because it would cause synthetic points to be "leaked") and compare CV F1 with the F1 score obtained from the class weighted setting.

6. Function Workflow

To demonstrate how a brand new patient's raw data goes through the trained pipeline with trained features to generate a useful “statin or no?”

output, predict_stroke_risk() would take the patient data, impute it with the same features used for the training (age_group, glucose_risk), pass it through the same pipeline of preprocessing and Random Forest, and then return the resulting probability as a three-level "statin or no?" label which the physician would be able to act on.

def predict_stroke_risk(patient: dict, model=best_model):
    df_in = pd.DataFrame([patient])
    df_in = engineer_features(df_in)
    proba = model.predict_proba(df_in)[0, 1]
    tier = 'HIGH' if proba >= 0.5 else ('MEDIUM' if proba >= 0.2 else 'LOW')
    return proba, tier

7. Discussion

Strengths

  • This pipeline addresses the class imbalance two different ways (class weighting, SMOTE), and checks which is better using CV F1 instead of taking one of them as granted.
  • It leverages a leak-free scikit-learn Pipeline, integrates annotations on two engineered features that rely on clinical thresholds (high-glucose flag, age bands) and provides comparisons of three model families ranging from an interpretable baseline to a boosted-tree model, for individual- prediction explanations using SHAP.

Limitations

  • Only ~249 positive cases, in a dataset of 5,110, is a too small sample for a rare 'event' (such as a case); the facts in performance estimate (particularly recall) are unconfirmed with wide uncertainty and should be re-validated on a larger, prospective sample before use at deployment time.

  • No timescale information (e.g. duration of hypertension) is available in the data set and so, there is limited ability for the model to learn the "risk trajectory".

  • There is a large category of smoking status that is not smoking, which may be associated with other factors, such as age (likely, and changes in data collection may be a hidden variable), and may be a hidden confounding variable.

  • SMOTE creates synthetic instances in the feature space; sometimes produces unnatural values (e.g., a child with a senior's risk profile), but causes them and goes against class weightings so be careful before believing it.

Business implications & recommendation

They tend to be very consistent factors: age, average glucose level, hypertension and heart disease which all seem to represent findings from clinical factors, which reassuringly agrees with current clinical risk factors.

Ideally, a tolerant deployment is not an accept/reject gate, but rather a “risk”-based tool: patients whose probabilities exceed some chosen cut-off (adjustable based on the PR curve, with the trade-off being that a higher cut-off means that a patient with a true positive will be missed, but a lower cut-off results in more false alarm flagged for clinician manual review, which is more costly than a true positive missed).

Explainability.

Explainability of the model at a patient level and at a global level: the Random Forest's feature importances plus the SHAP summary plot provide information on what were the factors that moved a patient's risk score higher.

###Deployment

As a decision support signal in addition to clinical judgement — the threshold and feature importances should be periodically verified as new patient data is acquired and retrain regularly.

However, the model should not be considered as a standalone/ automated decision for care, as the number of instances of positive class is limited.
